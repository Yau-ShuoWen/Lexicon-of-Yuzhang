# 南昌话拼音读写与用户设置设计

## 目标与范围

在设置页「通用设置」增加开关「使用旧版本南昌话拼音读写」，默认关闭。关闭时采用合并后的正式输入和显示规则；开启时，当前用户在网站中输入和看到的南昌话键盘拼音使用旧规则。内部音节、数据库拼音、其他方言、IPA 和词典资料不随开关改变。

本次同时建立可容纳后端设置的通用框架。现有显示语言、拼音框顺序、音效和日历称呼仍是设备设置；旧版南昌话拼音开关是首个账号设置。未登录时固定使用正式方案，开关不可用。

## 现状

- `yuzongweb/src/utils/userSettings.js` 使用单一 `localStorage` 对象，`saveUserSettings` 派发同页事件，`storage` 事件负责跨标签页通知；`SettingsPage.vue` 对整个响应式对象进行深度监听并立即保存。
- `request.js` 已自动在请求头加入 `X-Auth-Token`；`AuthController` 的 `/api/user/me` 和 `UserService.getUserByToken` 可取得稳定的用户 ID。`AdminAccessFilter` 跳过 `/api/user`，用户设置接口必须自行校验登录，不得要求管理员权限。
- `LACPinyin.tryOf(KeyboardPinyin)` 和 `toKeyboardPinyin()` 是拼音模型现有入口；`LACKeyboard.normalize` 当前将 `ee` 与 `ir` 都解析为 `ẹ`，输出则将 `ẹ` 写成 `ee`。改动这一公共行为会影响录入、回显和其他调用点，不应直接修改为按当前用户分支。

## 规则边界

定义 `KeyboardScheme`：`STANDARD`、`LEGACY`。前端原样发送用户输入，不发送拼音方案请求头。后端过滤器根据令牌取得用户设置，把方案放进当前请求的上下文，并在请求结束时清除；未登录或过期令牌使用正式方案。读取数据库内部拼音并生成响应时按该方案格式化，接收用户拼音并保存时按同一方案解析。设置是用户偏好，不作为权限依据。数据库拼音继续使用独立的内部表示。

| 场景 | 规则来源 | 结果 |
| --- | --- | --- |
| 资料入库、迁移、批处理 | 固定的正式资料规则 | 唯一内部音节 |
| 用户录入南昌话拼音 | 当前账号的选择 | 唯一内部音节；通配输入不用于保存 |
| 用户查看键盘拼音 | 同一选择 | 对内部音节格式化 |
| 查词 | 查询输入规则 | 可返回多个音节；`e` 通配仅在此层 |
| 其他方言、IPA、数据库拼音 | 原规则 | 不变 |

`ee` 在两套规则中意义冲突，不能在同一次录入中自动猜测。正式方案须先明确一套无歧义的录入拼写，查询中的通配规则单独实现。实施前用音节全集列出两套规则的输入、输出和往返结果，尤其核对 `e`、`ee`、`ir`、声调及复合韵母。输入和输出使用同一方案，但 API 不接受客户端提交的「已转换内部拼音」作为权限或资料依据。

## 设置模型和接口

设备设置继续使用现有 `userSettings.js` 与本地存储。账号设置由独立模块调用后端接口，不与设备设置一起保存。切换账号时清空账号设置快照，加载完成前显示默认关闭并禁用开关，避免展示上一个用户的值。

后端只允许白名单设置键，不直接存储前端传来的任意 JSON。首个键为 `lacLegacyPinyinReadWrite`，布尔值，默认 `false`。接口：

- `GET /api/user/settings`：认证后返回已知账号设置的有效值和版本号，缺失行由服务层补默认值。
- `PATCH /api/user/settings`：请求体只包含待改动键，例如 `{ "lacLegacyPinyinReadWrite": true, "version": 3 }`；服务端校验键、值、版本和用户身份，原子写入，返回完整有效设置与新版本。

令牌从 `X-Auth-Token` 读取，经 `UserService.getUserByToken` 得到用户 ID；客户端不能指定 `userId`。版本号防止两个设备同时更新时静默覆盖。版本冲突返回明确错误，前端重新拉取当前设置后让用户重试。设置不是权限，不使用 `AuthorityCode`。

## 设置推送与同步

「推送」分三层，先实现必要层，不引入服务器长连接：

1. 同页：保存成功后更新设置状态；只有当前页面展示或编辑南昌话拼音时，重新挂载该视图并向后端读取，保留滚动位置。
2. 同浏览器其他标签页：使用 `BroadcastChannel`，不支持时退回 `storage` 事件；同一用户的其他标签页收到变更后按同样范围更新。
3. 其他设备：登录、页面启动和窗口重新获得焦点时向后端拉取；发现方案变化后按同样范围更新。只有确有实时跨设备需求时再增 SSE/WebSocket。

登录成功后加载账号设置；退出登录或切换账号时先清空账号快照。网络失败时显示错误。修改时仅 PATCH 变化的账号键，成功后更新受影响的当前视图；失败后重新拉取并显示中文错误。不要沿用设置页当前的 `watch(settings, ..., {deep:true})` 直接把整个对象写入后端。

## 数据库设计（由项目负责人手动执行）

采用通用的逐项设置表，主键 `(user_id, setting_key)`；另设用户级版本表，保证多个键共享同一个并发版本。首个键按布尔值序列化为 `true` / `false` 字符串；未来新增键须在服务端注册类型、默认值与校验。实施前需核对 `NC.user.id` 的实际类型与数据库版本；应以 `docs/数据库/用户设置表.sql` 为手动执行脚本：

```sql
CREATE TABLE NC.user_setting (
    user_id INT NOT NULL,
    setting_key VARCHAR(80) NOT NULL,
    setting_value VARCHAR(2048) NOT NULL,
    updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
        ON UPDATE CURRENT_TIMESTAMP(6),
    PRIMARY KEY (user_id, setting_key),
    CONSTRAINT fk_user_setting_user FOREIGN KEY (user_id) REFERENCES NC.user(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE NC.user_setting_version (
    user_id INT NOT NULL,
    version BIGINT NOT NULL DEFAULT 0,
    PRIMARY KEY (user_id),
    CONSTRAINT fk_user_setting_version_user FOREIGN KEY (user_id) REFERENCES NC.user(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

后端写入事务：锁定或创建版本行；比较客户端版本；校验所有键值；逐项 upsert；版本加一；提交后返回设置快照。读取时只读取白名单键，缺失键填默认值。不要预先给每个用户插入默认行；关闭状态由默认值表达。

## 实施顺序与验收

1. 确认正式方案的确定性录入拼写，列出两套方案的音节往返表，审计模型入口行为。
2. 手动建表后增加后端 mapper、service、controller；验证未登录拒绝、用户隔离、非法键拒绝、版本冲突。
3. 拆分前端设备与账号设置存储，接入登录/登出同步和页面订阅；验证双标签页及网络失败。
4. 在「通用设置」增加默认关闭的开关及中文保存状态。
5. 前端原样发送拼音，由后端根据账号设置按请求方案读写；静态审计所有 `tryOf` / `toKeyboardPinyin` 调用，确保资料迁移和其他方言不随用户设置变化。

实现已在独立分支开始：设置接口、开关、后端按账号设置读写和受影响视图更新已接入。前端不改写拼音输入，也不选择两套后端候选；后端只返回当前方案的键盘输入。数据库中的拼音注释在编辑读取时转换为当前方案，保存时还原为内部表示。SQL 尚未执行，需手动建表后才可联调后端。Maven 在当前环境不可用，Java 部分须在有 Maven 的环境编译验证。现有未提交改动已保留。
